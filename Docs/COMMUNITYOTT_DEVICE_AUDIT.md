# CommunityOTT Device & Session Device Binding Audit

## 1. Executive Summary

This audit establishes the architectural foundation for **Device Management & Session-Device Binding** in the **CommunityOTT** platform following the completion of Phase A (Authentication & Session Hardening). 

While Phase A successfully delivered server-side session revocation, refresh token rotation, and JWT `sid` binding, CommunityOTT currently lacks a dedicated **Device** domain entity and explicit device registration limits. Session records (`auth_sessions`) store unnormalized string attributes (`device_id`, `device_name`, `platform`) without a unified device tracking or enforcement layer.

This document outlines the design required to enforce CommunityOTT's product rule of **maximum 2 registered devices per account**, transactional race-condition protection, device replacement workflows, iOS client identification strategies, and OTT industry benchmarking.

## 3. Distinction Between Three Core Concepts

To prevent architectural overlap and bugs, CommunityOTT strictly separates three distinct entities:

```
                  ┌─────────────────────────────┐
                  │          User (1)           │
                  └──────────────┬──────────────┘
                                 │
                 ┌───────────────┴───────────────┐
                 │                               │
    ┌────────────▼────────────┐     ┌────────────▼────────────┐
    │    Registered Device    │     │    Registered Device    │
    │        (Device A)       │     │        (Device B)       │
    └────────────┬────────────┘     └─────────────────────────┘
                 │
   ┌─────────────┴─────────────┐
   │                           │
┌──▼───────────────────┐    ┌──▼───────────────────┐
│ Auth Session 1 (JWT) │    │ Auth Session 2 (JWT) │
└──┬───────────────────┘    └──────────────────────┘
   │
┌──▼───────────────────┐
│ Playback Session 1   │
└──────────────────────┘
```

1. **REGISTERED DEVICE**:
   - Represents physical hardware or an app installation bound to a user account.
   - Max 2 active registered devices per user account.
   - Persists across multiple logins, logouts, and token refreshes.
2. **AUTHENTICATION SESSION (`AuthSession`)**:
   - Represents a specific login session instance on a registered device.
   - Tied to short-lived JWT access tokens and rotated refresh tokens.
   - Multiple authentication sessions can belong to a single registered device over time (e.g. repeated logins after logging out).
3. **PLAYBACK SESSION (`PlaybackSession`)**:
   - Represents an active video stream (HLS video playback instance).
   - Governed by concurrent stream limits (e.g. 1 active stream at a time per user).
   - Tied to an active `AuthSession` and `Device`.

## 4. Device Information & Privacy Audit

### Permissible & Safe Attributes
To identify devices reliably without invading user privacy or collecting PII, CommunityOTT collects ONLY the following metadata:

| Attribute | Type | Example / Description |
| :--- | :--- | :--- |
| `device_identifier` | String | Stable Keychain UUID generated by app installation |
| `platform` | Enum | `IOS`, `ANDROID`, `WEB`, `TV`, `TABLET` |
| `device_model` | String | "iPhone 15 Pro", "iPad Air 5th Gen", "Chrome on macOS" |
| `os_version` | String | "iOS 17.4", "macOS 14.3" |
| `app_version` | String | "1.4.0 (Build 42)" |
| `display_name` | String | User-defined name or default ("Hardik's iPhone") |
| `first_registered_at` | Timestamp | Initial registration timestamp |
| `last_active_at` | Timestamp | Most recent activity / API call timestamp |

### Prohibited Data (Privacy & Compliance Rules)
- **NO PII or Invasive Fingerprinting**: Never collect MAC addresses, IMEI, serial numbers, precise GPS coordinates, canvas fingerprinting hashes, or installed app lists.
- **NO IP Address as Device ID**: IP addresses change across Wi-Fi/Cellular networks and MUST NOT be used to define a device's identity.

## 5. The 2-Device Business Rule Architecture

### Rule Definition
CommunityOTT enforces a hard limit of **2 active registered devices per user account**.

### Enforcement Flow During Login (`POST /api/v1/auth/otp/verify`)

```
Client sends OTP Verify Request + device_identifier
                     ↓
Find Device in DB WHERE user_id = :userId AND device_identifier = :deviceIdentifier
                     ↓
            Device Exists?
           ├── YES ──> Is Revoked?
           │            ├── NO ──> Update last_active_at → Issue AuthSession (SUCCESS)
           │            └── YES ──> Treat as New Device Registration Request
           │
           └── NO ──> Count Active Devices (WHERE user_id = :userId AND revoked_at IS NULL)
                        ↓
                 Count < 2?
                ├── YES ──> Register New Device → Issue AuthSession (SUCCESS)
                └── NO ──> Reject with HTTP 409 CONFLICT / MAX_DEVICES_REACHED
                           Return List of Current Registered Devices for Replacement UX
```

## 6. Device Replacement Architecture & UX Flow

When an account already has 2 active registered devices and a user attempts to log in from a 3rd device:

1. **Login Interception (HTTP 409 Conflict)**:
   - The backend denies session creation and returns error code `MAX_DEVICES_REACHED`.
   - Payload includes the 2 currently active registered devices (ID, display name, model, last active timestamp).
2. **User Selection**:
   - The frontend displays the **Device Replacement Modal**:
     - *Device A: Hardik's iPhone 15 (Active 10 mins ago)*
     - *Device B: Living Room iPad (Active 2 days ago)*
   - User selects a device to replace (e.g. Device B).
3. **Revocation & Swap Request**:
   - Frontend calls `POST /api/v1/devices/{deviceId}/revoke` (or re-submits login with `replace_device_id`).
4. **Cascading Server Actions**:
   - `Device B` state set to `revoked_at = now()`.
   - All active `AuthSession` records linked to `Device B` set to `revoked_at = now()`.
   - Associated refresh tokens are invalidated.
   - Any access tokens held by `Device B` immediately fail on subsequent requests via `JwtAuthenticationFilter`.
   - New `Device C` is registered and an `AuthSession` is issued.

## 7. Session ↔ Device Relational Model

`AuthSession` MUST contain a foreign key referencing `Device`:

- `User` 1 ── * `Device`
- `Device` 1 ── * `AuthSession`

### Why Multiple Sessions per Device are Required
A single physical device will generate multiple authentication sessions over time:
- User logs out and logs in again next week -> Same `Device`, new `AuthSession`.
- User clears app state or token expires -> Same `Device`, new `AuthSession`.

## 8. Device Revocation & Logout Design

### Device Revocation API
`POST /api/v1/devices/{deviceId}/revoke`

- **Authorization Check**: Enforces that `device.user_id == currentPrincipal.userId`.
- **Action**:
  1. `UPDATE devices SET revoked_at = NOW() WHERE id = :deviceId AND user_id = :userId`.
  2. `UPDATE auth_sessions SET revoked_at = NOW() WHERE device_id = :deviceId AND revoked_at IS NULL`.
- **Security Outcome**: Prevents unauthorized remote access and instantly terminates all active JWT access tokens for that device.

## 10. Device Deletion vs Revocation Semantics

CommunityOTT adopts **Explicit Revocation Semantics** (`revoked_at IS NOT NULL`) over hard SQL deletion (`DELETE`):

- **Auditability**: Preserves historical logs of device registrations for security analysis.
- **Re-registration Handling**: If a revoked device attempts to log in again, the server updates its status back to active (if count < 2) or prompts for device replacement.

## 11. iOS Client Device Identification Strategy

To identify an iOS device reliably and in compliance with Apple App Store guidelines:

1. **Keychain-Backed UUID Generation**:
   - On first app boot, check iOS Keychain (`kSecClassGenericPassword`) for key `com.communityott.device_uuid`.
   - If missing, generate `UUID().uuidString` and store it in the Keychain.
   - **Why Keychain**: Unlike `identifierForVendor` or user defaults, iOS Keychain values persist across app uninstall and reinstall cycles!
2. **Device Metadata Helper**:
   - Retrieve `UIDevice.current.model`, `UIDevice.current.systemVersion`, and app version string from `Bundle.main`.
3. **Prohibited iOS Identifiers**:
   - Never use `ASIdentifierManager` (IDFA) unless running ad tracking.
   - Never query MAC addresses or hardware serials.

## 13. Security Analysis & Concurrency Protection

### Race Condition Threat Scenario
If two concurrent login requests from Device C and Device D arrive at the exact same millisecond for a user currently having 1 registered device:
- Both threads execute `SELECT COUNT(*) FROM devices WHERE user_id = X AND revoked_at IS NULL`.
- Both threads see `count = 1`.
- Both threads insert a new device -> **Result: 3 active devices registered, bypassing the product rule!**

### Required Transactional Lock Strategy
To prevent concurrency bypass:
1. **Pessimistic Locking**:
   In `DeviceRepository`, execute `SELECT u FROM User u WHERE u.id = :userId FOR UPDATE`.
2. **Sequential Registration**:
   Holding the pessimistic lock on `User` forces concurrent device registration requests for the same user to execute serially.

## 15. Proposed Data Model (Schema & Flyway V20)

```sql
-- Flyway Migration: V20__create_devices_and_link_auth_sessions.sql

CREATE TABLE devices (
    id BIGSERIAL PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    device_identifier VARCHAR(255) NOT NULL,
    platform VARCHAR(32) NOT NULL,
    device_model VARCHAR(255),
    os_version VARCHAR(64),
    app_version VARCHAR(64),
    display_name VARCHAR(255),
    first_registered_at TIMESTAMP WITH TIME ZONE NOT NULL,
    last_active_at TIMESTAMP WITH TIME ZONE NOT NULL,
    revoked_at TIMESTAMP WITH TIME ZONE,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW(),
    CONSTRAINT uk_user_device_identifier UNIQUE (user_id, device_identifier)
);

CREATE INDEX idx_devices_user_active ON devices(user_id) WHERE revoked_at IS NULL;
CREATE INDEX idx_devices_identifier ON devices(device_identifier);

-- Add Foreign Key to auth_sessions
ALTER TABLE auth_sessions ADD COLUMN device_entity_id BIGINT REFERENCES devices(id) ON DELETE CASCADE;
CREATE INDEX idx_auth_sessions_device_entity ON auth_sessions(device_entity_id);
```

## 17. Test Plan Overview (14 Scenarios)

1. First device registration succeeds.
2. Second device registration succeeds.
3. Third device registration rejected with HTTP 409 `MAX_DEVICES_REACHED`.
4. Login from existing registered Device A succeeds without increasing device count.
5. Device swap (revoking Device B to add Device C) succeeds.
6. Revoking Device A revokes all associated `AuthSession` records.
7. Access token for revoked device fails on next API request (HTTP 401).
8. Refresh token for revoked device fails (HTTP 401).
9. Logout-all revokes all devices and all sessions for user.
10. User A cannot view or revoke User B's device (HTTP 403 / 404).
11. Concurrent registration requests (Thread 1 & Thread 2) correctly enforce max 2 devices via `FOR UPDATE` lock.
12. iOS Keychain UUID persistence test across app reboots.
13. Duplicate `device_identifier` registration updates `last_active_at` rather than duplicating.
14. Malformed or blank `device_identifier` rejected with HTTP 400.
